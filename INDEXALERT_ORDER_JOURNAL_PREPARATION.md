# Durable order-intent journal — offline preparation

The broker-neutral SQLite journal persists an immutable intent identity and submission claim before any future sender could run. Separate concurrent connections cannot claim the same intent twice. Unknown outcomes survive restart and require recovery/reconciliation; a pending uncertain order blocks new submissions across other intent keys. Duplicate execution IDs are idempotent, conflicting executions are durably quarantined, partial-fill/cancel races preserve executed quantities, and terminal status cannot be resurrected by stale snapshots. WAL plus FULL synchronous mode and immediate transactions protect local durability; they do not establish broker truth.

This is standalone structural preparation, with no network, credential, broker adapter, sender, real-order authority or genuine LIVE evidence. Its snapshot inputs are offline diagnostic inputs and are not independently admitted broker records. It must not be wired to a sender until an independently validated adapter binds account/order/execution identity, market/session/freshness/NetEV checks, canonical gate admission, startup recovery, independent risk/kill controls and the authorized staged release. The journal does not implement amend/replace requests or operational Kill Switch actuation. One journal must cover the complete automated account scope for its global uncertainty interlock to apply. Intent identity must be stable across retries and must not include a retry counter. Quantity-only executions are not a PnL/evidence ledger.

Validation: 16 synthetic/offline tests cover simultaneous claims across SQLite connections, process-style close/reopen, timeout, acknowledgement after uncertainty, duplicate/conflicting executions, overfill rollback/quarantine, cancellation/late fill races, global unresolved-state interlock, stale terminal snapshots, rejected orders and malformed inputs. No synthetic result can satisfy the frozen execution sufficiency protocol.

Unchanged: frozen Alpha/cutoff/model/threshold/selection criteria, consumed holdout records, KRX source gates and LIVE provenance/promotion criteria. This module is development-only and is not deployed into the production order path.

## Persistent offline stop control — 2026-10-05

Every startup/reconnect returns local diagnostics to MASTER_OFF and invalidates prior safety epochs. SHADOW enable and Kill Switch reset are explicit compare-and-swap operations against the current epoch; a reset remains OFF. A killed latch survives reconnect and cannot be removed by disable/enable. Uncertain submissions, cancel outcome uncertainty, event/payload conflicts and inconsistent snapshots stop new local claims. Unresolved order state blocks re-enable/reset. Broker-order identity is unique within the account-scoped journal, and repeated fill attempts cannot override a preserved rejection.

claim_submission now requires expected_epoch from an explicitly enabled SHADOW state. This is a breaking fail-closed change for the standalone diagnostic API: absence, malformed values and old epochs are rejected. A SHADOW epoch is not a bearer credential, broker permission or independent gate-admission proof. Kill stops local diagnostic claims only, with no broker cancellation/liquidation. A future admitted adapter must recheck independent controls immediately before actual broker I/O, reconcile already in-flight requests, and supply its own access control and full operational safety integration. SQLite connections should be opened before explicit arming; opening another connection deliberately disarms and quarantines open activity.

Additional validation covers default OFF, restart OFF, durable Kill latch, explicit reset staying OFF, stale epoch invalidation, unresolved reset refusal, post-reconciliation OFF, strict epoch types, two-intent broker binding collision, payload collision stop and persistent rejection semantics. 29 journal/stop-control tests and 16 existing development control tests pass locally (45 total). No real-account, model, cutoff, holdout or empirical criteria change.
