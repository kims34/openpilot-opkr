## Why a generic 'registration normal' answer is not enough

- The owner's registered-IP Windows machine previously had at least one successful REAL OAuth token plus read-only REST account lookup, followed by a separate WebSocket LOGIN error (top-level `return_code=805004`, embedded `8050`). This is a *historical owner-reported outcome*, not a fresh observation.
- The official Kiwoom Python SDK categorizes `8050` in `DEVICE_AUTH_CODES`; its `AUTH_RETRY_RETURN_CODES` are `8005`, `8031`, `8103`, **not 8050**. Merely refreshing a token and retrying cannot be justified as a fix.
- The official SDK uses `wss://api.kiwoom.com:10000/api/dostk/websocket` and a `LOGIN` packet with `trnm` and newly issued `token`; the isolated smoke matches that format. A protocol mismatch is not established.
- Kiwoom's official service guide explicitly distinguishes *registered IP* and *account registration* under the REAL account App Key flow. Confirmation of an IP registration alone does not prove the account, App Key and WebSocket device/session authorization were checked together.
- The separate Railway REAL services have no independently verified successful LOGIN/Type00 event. A Railway deployment marked `SUCCESS` only means the deployment step succeeded; it does not establish broker authentication.

Official references:
- https://openapi.kiwoom.com/intro/serviceInfo (IP registration followed by account registration and REAL App Key)
- https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/core/errors.py (8050 category and one-shot retry code allowlist)
- https://github.com/Kiwoom-Securities/Kiwoom-REST-API/blob/main/kiwoom/core/ws_client.py (WS LOGIN format and error response handling)

3. Is the credential's registered REAL account authorized for WebSocket LOGIN and Type00 (`00`) real-time order/fill subscription, or is there a separate API entitlement or account/device binding condition? We are not requesting you to enable trading or change permissions yet.
4. Was the source egress IP / designated terminal identity that the **WebSocket server actually saw** the same as the one bound to the REAL App Key? Can you verify this internally using the owner's privately provided event time/IP? We will not post it publicly.
5. Is `8050` generated by an IP-registration check, a separately maintained designated-terminal rule, an App Key/account binding rule, or a session/device attestation check in this scenario? If you cannot disclose internals, please provide a concrete owner-side diagnostic step.
6. Does the token become invalid for WS when a read-only REST account call is made first, or is a single freshly issued token reusable across REST and WS as described in the official SDK?
